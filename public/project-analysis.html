WE-ADK — Stack & Process Flow

What the system is built on, the path a customer conversation takes to become shipped code, and the mechanics underneath it.

What it is

WE-ADK is an AI-assisted product development pipeline: four tools inside one project, carrying work from a customer meeting through to running code. Every stage shares one Claude engine, and the whole stack is cloned and customised per business line — BZP, BIZ, Local Currency, Voucher, KOSIGN. The eACC Cloud screens in this same app are not a second product so much as the worked example: version 1 of a real project, walked as 25 live screens.

Full process flow

The path from a customer conversation to shipped code. Blue markers are steps where Claude does the work; grey markers are human decisions.

Discovery— Sketcher, one round per meeting

Customer meeting Human

A PM comes out of a meeting with notes, decisions, open questions and reference material — the customer's own sheets, a transcript, an RFP.

Notes become concept screens Claude

The notes and extracted reference text are sent to Claude, which proposes the screens they imply — pre-requirements, favouring clarity over completeness, inventing nothing the customer did not raise. Where a production screen already exists, it proposes the revised version of that screen instead of designing from scratch.

Screens land as editable blocks Human

Each proposed screen arrives on the board as a stack of typed blocks — headings, inputs, tables, button bars. The PM rearranges them on the block canvas, then asks the customer "is this what you meant?"

The round is frozen as a version Human

Version 1 is the baseline — every concept design the meetings produced, in one place, and read-only so the record of what was first agreed stays intact. The next design creates version 2, and each round after that gets its own version folder.

Consolidation— many meetings become one design

Contradictions are surfaced, not silently resolved Claude

Sketches drawn one meeting at a time overlap and contradict each other. Everything the project knows is assembled into a single context block and consolidated into one canonical screen set, the decisions that constrain it, and — separately — the contradictions a human still has to settle.

Structure, work and actors are defined Human

The IA tab fixes information architecture and screen order, Task captures the work the round carries, and User defines the actors. Overview reads all three back.

The round is written up as a document Human

A business analyst hands the round to people who will never open the app: screens, order, work, decisions and open questions, exported as Markdown for a repository or HTML for a browser.

Specification— Builder

Solution mockups become work mockups Human

Planners turn the agreed concept into screens that actually work, against an assigned design system so components and tokens are settled rather than argued.

The formal handoff package is assembled Human

Requirements spec (PRD), feature specs, screen designs, unit and integration test definitions, and user manuals — the eight Builder tabs — become the contract development builds against.

Development— Developer, one task at a time

A task enters the Build workspace Human

One task moves through four stages — Build → Test → Review → QA. A stage can fail (the work is wrong) or block (the work cannot proceed: a missing decision, an unavailable dependency); the two get different responses.

Claude Code executes against a real clone Claude

Not a mock. The file explorer lists an actual git checkout decorated with git status, so what "exists" and what "changed" are the repository's answers. Claude builds with the business unit's rules and domain context in scope.

The product renders live, then checks run Human

The work renders as a running product while it is built. Checks run, the diff is reviewed, and the task is handed to QA — which can be shared out by token link to a reviewer with no account.

Operations— DevAdmin, continuous

Usage, cost and security are watched across the org Human

Every Claude run reports duration, cost, token counts and model. DevAdmin aggregates that by group, project and user, alongside token administration and security review — the control layer that makes AI-assisted development safe to scale.

Inside a Planner project — the six tabs

The tab order follows the work rather than importance: the round's task is agreed, someone drafts against it, Main is what that settles into, and the Dashboard reads all three back. Every tab is scoped to the round selected on the version rail, and a released round is read-only everywhere.

Dashboard/overview

The round read whole. Main, Task and Member are all working views answering "what am I doing next" — nothing answered "what is this round", which is the question asked at a hand-off, at a status meeting, and by anyone who did not sit through the round being built. This reads across the other tabs and puts that answer in one place, then exports it as a zip, because the people asking usually do not have the app open.

Main/ · the default

The design files themselves, in a version explorer that behaves like an editor's file tree: the project nav and the tree stay mounted, and opening a file swaps only the pane on the right. Main is one tab with four views, and the tab stays lit across all of them.

Files/sketcher
The tree — project → version → design file. Version 1 is the locked baseline; each later round gets its own folder. Files are added by generating from notes, copying a screen that already runs in production, or starting blank.
Board/board
The round's frames laid out together, beside the meeting notes they came from. This is where "Generate screens" is pressed — notes in, proposed screens out — and where a generated set is materialised into real design files.
Canvas/canvas?screen=…
One screen, edited as an ordered stack of typed blocks — headings, inputs, tables, button bars. Blocks are dragged with dnd-kit, and each one maps to the design-system component that governs it, so clicking a block points at the spec rather than at a guess.
Preview/preview
The screen rendered as a real page, with the chat pane beside it for review and edits, and an export to standalone HTML.
IA/ia

The round's screens as one flat sitemap sheet — one row per screen, its folder spread into depth columns, the shape a real IA document takes. It seeds itself from the round's files so it never opens empty, and any edit freezes to its own overlay, so a rename here cannot fight the file it was drawn from.

Task/task

The work the round carries: title, description, category, tags, comments and attachments. A task is already a brief, so it can be handed straight to the screen generator — and the pane remembers which designs came out of which task, so it can link back to them. A design generated from a task goes to the person who owns the task rather than into the round directly. This is also where the Excalidraw whiteboard lives, for sketching a task out by hand.

Member/user

Who is on the team, and each person's own workspace of forked screens. It started inside this tab and moved into shared code once Task needed it too, so both tabs write to the same place and agree on what a workspace is. Browser-only — every member and every forked screen lives in localStorage.

Setting/setting

Project-level conventions rather than preferences: the screen ID suffix format, IA depth configuration, and regenerating screen IDs across the project when that format changes.

How it works

One Next.js process serves the UI and the API. When a screen needs AI, the route handler spawns your local Claude CLI as a child process and returns parsed JSON — there is no model API in the app.

Tools are switched off — and the two paths do it differently

These routes only ask Claude for text or JSON, so each run is capped at a single turn with no session persistence, and the CLI is launched outside the repo so the project's own CLAUDE.md is never auto-loaded. The chat route empties the tool set with --tools "". The shared bridge behind generate, consolidate and the Developer prompt passes --allowed-tools "" instead — which a code comment in the chat route states does not actually empty the set, leaving every tool in place. Worth a look: the two paths are not equivalent, and only one of them uses the flag the codebase says works.

Every user brings their own Claude account

The browser sends the token from claude setup-token on each request and the CLI runs as that account. Host credentials — ANTHROPIC_API_KEY and six siblings — are stripped from the child environment, and the config directory is moved outside ~/.claude so the host machine's own login can never be picked up. Usage is therefore attributable per person, which is what DevAdmin reports on.

13 of the 14 routes refuse non-local requests

Every AI and workspace route checks that the request arrived on localhost and rejects it otherwise — the code comments say plainly that this exists because the app has been exposed through a tunnel before. Only /api/prototype/[slug] is public. Over a tunnel the UI loads and browses, but generation, chat and the Developer console are off unless SKETCHER_AI_ALLOW_REMOTE=1 is set. That is the guard working, not a fault.

Persistence is the browser

Design files, canvas edits and versions live in localStorage, keyed by version. Work survives a reload without pretending there is a backend — but it is per-browser, and clearing site data clears the project.

Production builds statically export, which drops the API

output: 'export' is set whenever NODE_ENV is production, and a static export cannot serve route handlers. Every endpoint above exists in development and disappears from the deployed artifact — which is why a duplicate copy of the API is kept under src/app/_api/ as the workaround.

How the AI chat works

The chat is not one assistant with a system prompt. It is a Claude Code terminal pinned to whatever you have open, and the folder it is pinned to decides both what it can see and what it is allowed to do.

1 · It streams, rather than waiting

Generate and consolidate buffer a single JSON envelope and return it when the model is done. The chat does not. It spawns the CLI in stream-json mode and forwards its NDJSON lines to the browser as they arrive — the same events the real Claude Code UI is drawn from — so text appears the moment the model produces it, and the stop button cancels a run that is already underway.

2 · The folder is the context

Each conversation is pinned to one folder and receives everything that folder knows — notes, decisions, reference files, sketches — up to 16,000 characters, plus the last 30 turns. The instruction is explicit: it knows only what is in that context, and if the folder does not answer something it says so rather than inventing. Answers are terminal-style — direct, concrete, no pleasantries, short answers to short questions.

3 · Where you are decides who it is

The folder label selects one of six roles, each with its own skills — and, importantly, its own limits.

WhereRoleWhat it doesBuilds UI
MeetingMeeting assistant Brainstorms ideas, spots what the notes are missing, and rewrites the notes on request Yes
ResearchResearch analyst Summarises and compares reference files, quotes its source so you can verify, extracts requirements and user stories into tables Yes
PreviewDesign reviewer & code editor Reviews layout, hierarchy and flow; edits the screen's HTML in place, applying only what was asked rather than redesigning Yes
Version folderDesign lead Reads across every file in the round — cross-screen consistency, navigation gaps, screens the round is missing Yes
TaskTask assistant Breaks work into subtasks, drafts acceptance criteria and test cases, flags overlap with other tasks in the round No — by design
Project rootDesign assistant Plans what screens the project needs, suggests flows and information architecture Yes

The Task role is the interesting one: it is explicitly forbidden from emitting HTML or designing screens, and told to redirect you to the Main tab instead. Design happens where designs are stored.

4 · The reply is a control, not just text

Two fenced block types are intercepted before the reply is rendered, which is what makes the chat part of the workflow rather than a sidebar to it.

A notes blockRenders with an Apply to Notes button. The model is told to output the complete notes, not a diff, so accepting is a clean replacement.
An html blockAuto-saved as a design file and rendered in the preview. The model is instructed to return the code block only — no text around it — because the system is parsing, not reading.

Generated HTML follows a fixed house style carried in the prompt: all CSS inline, no CDN links or Google Fonts, 8px spacing grid, system font stack, semantic status colours, and realistic seed data. The result is a standalone file that opens anywhere.

5 · What you control per turn

ModelOpus 5, Sonnet 5 or Haiku — Haiku is the default, so the cheap model handles the common case.
Extended thinkingToggled per turn, not per session.
EffortLow, medium or high — mirroring Claude Code's own setting.
AttachmentsUp to four. Images go as base64 (~2 MB cap); text files are read in the browser and inlined.
File mentionsReference a project file directly in the message.
VoiceDictation in, read-aloud out.
UsageEach run reports duration, cost, tokens and model — this is what DevAdmin aggregates.
TimeoutFive minutes per run, then the process is killed.

The chat talks about the folder; it cannot touch it

A text-only turn runs with --tools "" and a one-turn cap: the assistant reads the context it was handed and writes text back, with no filesystem access. Attaching an image is the single deliberate exception — the run is granted Read scoped by absolute glob to that attachment's temp folder and allowed four turns, so it can look at the picture and nothing else. Either way, nothing lands in the project until you press Apply or a fenced HTML block is saved as a design file.
